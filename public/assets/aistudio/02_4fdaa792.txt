# 1\. 产品定位与建设目标

## 1.1 产品定位

GlobalCodeTrans V2.0 是面向跨境投资、设备贸易、工程建设、技术合作、并购尽调及专业技术资料处理的专业文档智能处理与多语种翻译系统。系统不是单纯的文本翻译器，而是以文档结构理解为基础，完成文件解析、对象识别、专业翻译、图表/公式/工程图保真处理、结构重建和可编辑 Word 输出。

## 1.2 核心目标

* 对 PDF、图片及可支持的办公文档进行内容提取，并尽可能保留页面结构、对象位置、图文关系和原始证据。
* 对中文、英文、老挝语及后续扩展语种进行专业级互译，支持文档级上下文、术语一致性和数值/单位保护。
* 识别并分类处理文本、表格、数学公式、曲线图、统计图、流程图、CAD/工程图及其他嵌入对象。
* 对于能够可靠恢复的对象进行结构化重建；对于无法可靠恢复的对象保留原始对象并明确标记，不得伪造数据。
* 输出可编辑、可审校、可追溯的 Word 文档，支持双语对照及按业务需要选择的版式模式。
* 通过真实文件、真实输出和量化指标验收，不以代码存在、界面展示、日志模拟或固定 PASS 代替实际能力。

## 1.3 设计原则

| 原则 | 执行要求 |
| :--- | :--- |
| 证据优先 | 原生 PDF 对象、原始图像和确定性算法结果优先于模型推断；所有关键结果保留来源。 |
| 保真优先 | 优先保留原文档内容、数值、单位、编号、对象关系和几何信息，不为版面美观擅自改写事实。 |
| 可编辑优先 | 能恢复为文本、表格、公式或矢量图形时，优先生成可编辑对象；不能可靠恢复时保留原图。 |
| 模块可替换 | 识别、翻译、重建引擎通过适配器接入，不将单一供应商或单一模型写死在业务流程中。 |
| 真实验收 | 每个能力状态必须由真实调用和有效输出证据支持；测试数据与正式业务数据隔离。 |
| 不确定性显式化 | 低置信度、冲突、缺失、无法识别和人工待审均须明确呈现，不自动补造。 |
| 界面稳定 | 除非用户明确提出，不改变现有 GUI 的整体布局、颜色、按钮层级、用户操作流程和既有功能。 |

# 3\. 产品范围、功能边界与非目标

## 3.1 首期核心范围

| 能力域 | 首期要求 | 边界说明 |
| :--- | :--- | :--- |
| 文件接收 | 支持 PDF、常见图片格式；支持后续扩展 DOCX 等 | 保留原始文件，不因文件名或页数推测内容 |
| PDF 解析 | 文本、页面、字体、矢量路径、嵌入图像、坐标和页面属性 | 扫描 PDF 与原生 PDF 分流处理 |
| 页面与对象识别 | 区域检测、对象分类、对象关系、置信度与证据 | 允许 UNKNOWN，不强制所有对象归类 |
| 公式处理 | 公式区域检测、结构识别、LaTeX/结构化表达及可编辑重建 | 低可信公式保留原图并标注待审 |
| 图表处理 | 坐标轴、刻度、图例、曲线/数据系列识别与数据恢复 | 无法可靠恢复数据时不绘制虚构曲线 |
| CAD/工程图 | 通过已验证 CAD 插件处理可支持的图形数据与文字 | 沿用用户已验证插件，不重新论证插件可行性 |
| 专业翻译 | 文档级上下文、术语库、数字单位保护、多语种翻译 | Gemini 为首选主翻译引擎，支持替换 |
| 文档重建 | 图文/表格/公式/图表按能力重建，保留原始对象 | 提供可编辑与原图保留两种策略 |
| Word 输出 | 双语段落对照、表格和对象排版、原文/译文审校 | 版式优先级需由用户界面选项控制 |
| 任务与审计 | 进度、日志、异常、引擎调用、对象级状态和导出 | 进度必须来自实际任务状态 |

## 3.2 明确非目标

* 不开发 AutoCAD、Origin、MathType 等专业桌面软件的完整替代品。
* 不要求首期部署本地大语言模型；不要求用户安装一组复杂专业环境。
* 不承诺所有低清扫描图、复杂公式、复杂工程图均可自动达到原生精度。
* 不自动补齐原文件缺失的尺寸、公式、坐标、曲线数据、标准条款或法律依据。
* 不以“视觉上相似”作为图表数据正确或工程图几何正确的证明。
* 不在未经用户确认的情况下重构现有 GUI 或改变用户已熟悉的操作流程。

# 4\. 端到端业务工作流

| 步骤 | 系统行为 | 主要输出/状态 |
| :--- | :--- | :--- |
| 1 文件导入 | 读取用户选定文件，校验格式、大小、可读性并生成任务 | 源文件记录、任务 ID、导入结果 |
| 2 文档预检 | 识别页数、页面尺寸、旋转、文本/图像/矢量分布和可解析性 | 文档概况、页面清单、预检告警 |
| 3 原生解析 | 提取 PDF 文本、字体、坐标、矢量路径、图像及引用关系 | 原生解析对象及证据 |
| 4 页面理解 | 页面渲染、版面区域检测、对象识别和关系构建 | 页面布局、对象候选、置信度 |
| 5 专业路由 | 按对象类型和证据选择 OCR、公式、图表、CAD 等引擎 | 引擎执行记录、对象级输出 |
| 6 结果融合 | 去重、冲突处理、可信度评估和人工复核标记 | 统一 Document IR |
| 7 翻译准备 | 构建文档上下文、术语表、保护片段和分块 | 可翻译单元及术语约束 |
| 8 翻译与复核 | 调用 Gemini 或经批准的替代引擎，执行一致性检查 | 译文、差异、质量标记 |
| 9 对象重建 | 按 A/B/C 策略重建文本、表格、公式、图表或保留原图 | 结构化对象及布局信息 |
| 10 Word 组装 | 生成双语段落、表格、图形、页眉页脚和目录等 | DOCX 文件 |
| 11 质量检查 | 执行内容完整性、数值一致性、对象遗漏和版面检查 | 检查报告、待审事项 |
| 12 导出与归档 | 交付 Word、必要的 PDF 预览和结构化任务记录 | 最终文件、可追溯任务记录 |

工作流应支持任务暂停、失败重试、单页/单对象重处理和结果版本管理。重处理不得无提示地覆盖已人工确认内容；必须保留历史版本或差异记录。

# 5\. 总体技术架构

## 5.1 架构模式

建议采用模块化单体（Modular Monolith）作为首期部署形态，内部按业务域分层、通过稳定接口连接；外部识别/翻译引擎采用可插拔适配器。首期不因模块数量多而拆分微服务，以降低部署、网络、调试和维护成本。若 AI Studio 实际运行环境对后台任务、外部服务或文件存储有明确限制，须提出可行替代架构。

## 5.2 七层逻辑架构

| 层级 | 职责 | 关键模块 |
| :--- | :--- | :--- |
| L1 文件接收与任务层 | 文件导入、校验、任务创建、源文件与任务状态 | File Intake、Task Manager、Storage Adapter |
| L2 原生信息提取层 | PDF 原生文字、字体、矢量、图像和页面元数据提取 | PDF Native Reader、Asset Extractor |
| L3 页面理解与对象检测层 | 渲染、版面分析、对象检测、页面/对象关系识别 | Page Renderer、Layout Analyzer、Object Detector |
| L4 统一文档对象模型层 | 将各引擎结果统一为可追溯、可编辑的 Document IR | Document IR、Coordinate Mapper、Relation Graph |
| L5 多引擎调度层 | 按对象类型、质量和环境选择引擎 | Engine Registry、Router、Adapters |
| L6 结果融合与质量控制层 | 去重、冲突处理、置信度、证据、人工审核 | Fusion、Validation、Review Queue |
| L7 翻译、重建与输出层 | 专业翻译、术语管理、对象重建、Word 组装和导出 | Translation、Terminology、Reconstruction、DOCX Export |

## 5.3 关键架构约束

* 业务流程只依赖统一接口，不直接依赖某个识别模型的私有返回结构。
* 所有引擎输出先进入适配层，再映射为 Document IR；禁止各模块自行维护互不兼容的数据结构。
* 原始输入、引擎原始输出、融合结果、人工修订结果分层保存，不能只保留最终文本。
* 所有对象必须有稳定 ID、来源页码、边界框/坐标空间、来源引擎和处理状态。
* 模块调用关系应可观测；系统必须能够证明某引擎实际被调用并产生有效结果。
* 长任务采用可恢复的任务队列或等价机制；界面不得仅用定时器制造虚假进度。
* 外部服务失败时，系统应明确标记失败原因和可重试性，不得静默跳过后报告成功。

# 6\. 统一文档对象模型（Document IR）

## 6.1 目标

Document IR 是全系统的核心数据契约。PDF 原生解析、OCR、版面模型、公式识别、图表算法、CAD 插件、翻译和 Word 重建均通过 Document IR 交换结构化结果。它既要保存内容，也要保存几何位置、对象关系、来源证据、置信度和处理状态。

## 6.2 层级结构

Document → Page → Region → Object → Element → Content / Geometry / Data。一个 Region 可包含多个 Object；一个 Object 可由多个 Element 组成；跨页对象通过 relation 引用，不得复制成互不关联的独立对象。

## 6.3 核心字段

| 对象层级 | 建议字段 | 说明 |
| :--- | :--- | :--- |
| Document | documentId、sourceFile、fileHash、fileType、languageHints、pageCount、createdAt、status、metadata | 文档级信息及源文件指针 |
| Page | pageId、documentId、pageIndex、width、height、rotation、mediaBox、cropBox、renderInfo | 页面尺寸、旋转、渲染参数 |
| Region | regionId、pageId、regionType、bbox、readingOrder、parentId | 标题、正文、页眉、页脚、栏、表格区域等 |
| Object | objectId、pageId、parentId、objectType、bbox、coordinateSpace、sourceType、sourceReference、confidence、status | 文本、表格、公式、图表、图像、CAD 等对象 |
| Element | elementId、objectId、elementType、text、value、unit、style、geometry、sequence | 对象内部的字符、单元格、公式项、数据点等 |
| Evidence | evidenceId、sourceFile、pageIndex、bbox、rawContent、engineId、engineVersion、parameters、timestamp | 支持识别结果的原始证据 |
| Relation | relationId、fromId、toId、relationType、confidence、evidenceIds | 包含、相邻、标注、引用、连接、跨页延续等 |
| Review | reviewStatus、reviewer、reviewedAt、changeSet、reason | 人工审核和修订留痕 |

## 6.4 对象类型枚举

TEXT、PARAGRAPH、HEADING、LIST、TABLE、TABLE\_CELL、FORMULA、CHART、PLOT、DIAGRAM、FLOWCHART、CAD\_DRAWING、IMAGE、CAPTION、FOOTNOTE、HEADER、FOOTER、PAGE\_NUMBER、UNKNOWN。可扩展，但不得随意复用已有类型表达不同语义。

## 6.5 状态与置信度

建议对象处理状态：DETECTED、CLASSIFIED、EXTRACTED、STRUCTURED、TRANSLATED、RECONSTRUCTED、NEEDS\_REVIEW、FAILED、SKIPPED\_WITH\_REASON。置信度必须由可解释证据、模型分数或规则质量计算得出；无可靠分数时使用 UNKNOWN，不得统一写入固定值。

人工修改后，原始识别结果仍需保留；修订内容作为新版本或 changeSet 记录。人工审核状态不能抹除原引擎输出。

# 7\. PDF 原生解析与页面理解

## 7.1 原生 PDF 解析

保留 PDF.js 作为浏览器端 PDF 读取、渲染和文本提取的首选候选。除 getTextContent() 外，必须评估并实现可行的原生信息提取能力，包括页面框、旋转、文本项变换、字体信息、矢量绘制信息、嵌入图像和对象位置。具体 API 能力及版本兼容性由 AI Studio 在实际依赖版本中核验。

* 页面元数据：MediaBox、CropBox、页面尺寸、旋转角度、页序号、PDF 版本及可获得的元信息。
* 文本：字符/文本项、文本内容、字体、字号、颜色、变换矩阵、基线和边界框；尽量保留阅读顺序与原始片段。
* 矢量：路径、直线、曲线、闭合路径、填充/描边、颜色、线宽、变换矩阵和裁剪关系（以当前解析库实际可提供能力为准）。
* 图像：嵌入图像资源、原始尺寸、页面位置、变换矩阵、裁剪和渲染分辨率。
* 页面绘制对象：能可靠提取的对象应保留对象级引用；无法直接获得的内容需通过页面渲染和视觉算法补充。

## 7.2 页面分类

页面分类必须允许多标签，例如 TEXT\_HEAVY、IMAGE\_HEAVY、VECTOR\_HEAVY、TABLE\_HEAVY、FORMULA\_HEAVY、DRAWING\_HEAVY、MIXED、LOW\_QUALITY\_SCAN。不得仅以文本项数量少就推断页面含扫描图像，也不得仅凭存在图像就认定页面为扫描页。

## 7.3 原生提取与视觉识别的优先级

对同一内容，若原生 PDF 对象完整且可信，应优先使用原生提取；若原生信息缺失或质量不足，再使用 OCR/视觉识别；两者冲突时保留双方证据并进入融合规则，不得静默覆盖。

## 7.4 坐标体系

| 坐标空间 | 定义/用途 |
| :--- | :--- |
| PDF_USER_SPACE | PDF 文件原始用户坐标，保留原始坐标方向和单位定义 |
| PDF_PAGE_SPACE | 系统统一页面坐标：左上角原点，X 向右、Y 向下，单位 point |
| VIEWPORT_SPACE | PDF.js viewport 坐标，受缩放、旋转和页面视口影响 |
| RENDER_PIXEL_SPACE | 页面 Canvas 渲染像素坐标 |
| IMAGE_PIXEL_SPACE | 独立图像资源像素坐标 |
| ENGINE_SPACE | 外部识别引擎使用的坐标空间 |
| OUTPUT_SPACE | Word 或导出文档中的布局坐标 |

每个 bbox 必须携带 coordinateSpace。转换必须使用完整仿射矩阵或等价的严格变换链，明确处理 CropBox、MediaBox、页面旋转、viewport、缩放、图像变换和裁剪。禁止只用页面宽高比例进行简单换算。必须提供正向和逆向映射测试。

原生对象坐标转换的工程目标：在可可靠提取的原生对象上，转换偏差不超过 1 PDF point；若具体对象/解析库不具备达到该目标的条件，应在评估报告中说明适用范围和实际测量结果，不得虚报达标。

# 8\. OCR 与版面分析

## 8.1 OCR 策略

OCR 仅用于扫描文字、图片文字或原生文字提取不完整的区域。应尽量采用区域级 OCR，而非对整页重复 OCR。OCR 结果需保留文本框、行/段关系、阅读顺序、语言、置信度、图像裁剪引用和引擎版本。

## 8.2 版面分析候选

综合版面解析优先评估 MinerU，Docling 作为备选；不得未经整体评估就同时集成多个重量级解析框架。PDF.js 原生提取与专业版面解析互补：前者负责原生对象证据，后者负责复杂页面结构理解。

## 8.3 版面区域类型

TITLE、SECTION\_HEADING、BODY、PARAGRAPH、LIST、TABLE、FORMULA、FIGURE、CHART、CAPTION、HEADER、FOOTER、FOOTNOTE、SIDEBAR、UNKNOWN。阅读顺序应支持双栏、多栏、跨页表格和浮动图形。

## 8.4 OCR 质量控制

* 采用 CER（字符错误率）及必要时 WER（词错误率）评价；区分语言、字体、扫描质量和对象类型。
* 保留 OCR 原始文本与后处理文本，不能只保留语言模型润色后的结果。
* 专业术语、数字、单位、负号、小数点、上下标、编号应进入重点校验。
* 低置信度片段标记为待审核，不得用上下文猜测填补原图不可辨认内容。

# 9\. 公式识别、结构解析与重建

## 9.1 处理原则

公式处理必须区分公式区域检测、公式内容识别、结构解析和最终重建四个环节。公式区域检测不等于公式识别成功；识别出 LaTeX 字符串也不等于结构正确。

## 9.2 算法路线

| 场景 | 首选处理 | 候选/补充 |
| :--- | :--- | :--- |
| PDF 原生公式 | 优先分析原生文本、字体、上下标、矢量和布局结构 | PDF.js 原生对象、结构规则 |
| 扫描/图片公式 | 公式区域检测（MFD）+ 公式识别（MFR） | Pix2Text 候选；按实际环境评估其他模型 |
| 混排正文公式 | 先做版面/行内对象切分，再执行公式识别 | 文本与公式对齐、行内基线恢复 |
| 复杂多行公式 | 保留行、对齐点、编号、括号和矩阵结构 | LaTeX/MathML 或内部 AST |
| 低清或歧义公式 | 保留公式原图，输出候选及待审核状态 | 不得自动选择未经证实的表达式 |

## 9.3 结构数据

建议公式对象同时保存 rawImageRef、rawText、latex、mathml（若可得）、AST/结构树（若实现）、displayMode、inlineBaseline、numbering、confidence、evidenceIds。LaTeX 是交换表达，不应成为唯一事实存储。

## 9.4 误检治理

* 不得以数学符号正则或字母数字组合直接判定公式；需结合区域形态、排版特征、上下标、符号密度、行内位置和上下文。
* 不得将目录标题、页码、普通编号、表格标题、标准条款编号误判为公式。
* 必须对公式候选执行去重、合并、重叠处理和父子关系约束，避免同一公式被切成大量碎片。
* 不得使用固定置信度（例如统一 0.89）；置信度应反映实际模型输出或规则评估。
* 验收必须同时统计 Precision、Recall、F1、公式结构准确率、误检率、漏检率和重建可读性。

# 10\. 曲线图、统计图与数据恢复

## 10.1 目标

图表处理不仅是重绘外观，而是尽可能恢复图表的语义和数据：图表类型、坐标轴、刻度、单位、图例、数据系列、曲线/柱形/散点、数据点及图注。恢复结果必须能追溯到原始图像或 PDF 原生矢量对象。

## 10.2 处理流程

1. 图表区域检测：识别绘图区、标题、图例、坐标轴标签、刻度、单位、注释和图注。
2. 图表类型分类：折线、散点、柱状、面积、组合图、双 Y 轴、误差棒、等值线及 UNKNOWN。
3. 坐标轴标定：识别线性/对数轴、刻度值、轴方向、单位、断轴和坐标原点。
4. 数据系列分离：依据颜色、线型、标记形状、图例和几何连续性区分系列。
5. 数据点提取：恢复像素坐标到数据坐标的映射，保留采样密度和误差估计。
6. 语义复核：由 Gemini 等模型辅助解释标题、图例和变量含义，但不得由 LLM 凭空补数据。
7. 结果重建：生成可编辑矢量图/数据表，或在无法可靠恢复时保留原图并附提取结果。

## 10.3 算法候选

采用 OCR + OpenCV 类几何处理 + 图表数字化算法（可评估 WebPlotDigitizer/PlotDigitizer 类路线）+ Gemini 语义辅助。原生 PDF 矢量图表优先从路径、文本和图例对象恢复；栅格图表才重点依赖图像算法。

## 10.4 数据可信度

每条数据系列应记录坐标标定方法、轴类型、单位、采样点、像素坐标、换算后的数值、拟合/插值方法、误差估计和来源证据。若无法确定刻度或图例映射，输出 UNKNOWN/NEEDS\_REVIEW，不得自动生成貌似完整的数据表。

## 10.5 验收

使用具有已知原始数据的真实或受控测试图，计算数据点误差、曲线偏差、轴刻度识别准确率、系列识别准确率、图例映射准确率。必须分别报告线性轴、对数轴、多系列、双轴、低分辨率和复杂背景场景。

# 11\. CAD 与工程图处理

CAD 插件已由用户长期使用并验证可用，本项目不再将“CAD 插件是否可行”作为前置论证事项。系统应围绕已验证插件建立稳定的数据适配、调用、坐标映射、结果回读和质量对照机制。

* 明确插件输入输出格式、调用方式、版本、依赖、错误码和可支持实体类型。
* 将 CAD 图形中的文字、尺寸、线段、圆弧、多段线、块、图层和坐标信息映射到 Document IR 或专用 CAD 子结构。
* 保留原始 CAD 文件/图形引用；翻译仅作用于可识别文字对象，不擅自修改几何实体。
* 翻译后文字长度变化需考虑文字框、对齐方式、旋转角度和图层属性；无法适配时提示用户，不得移动关键几何对象。
* 输出前执行实体数量、关键坐标、尺寸标注、图层和几何闭合关系对照。
* CAD 插件的真实能力边界、接口和样本验证结果由 AI Studio 在整体评估中核对，不得虚构插件 API。

# 12\. 专业多语种翻译引擎

## 12.1 主引擎与调度

Gemini 作为首选主翻译引擎，承担专业语义理解、上下文翻译、术语辅助和译文复核。翻译服务必须通过统一 Translation Provider 接口调用，保留替换其他模型/服务的能力。模型名称、API 调用方式、配额和价格属于运行配置，不得写死在业务代码中。

## 12.2 翻译单元

按语义和文档结构划分翻译单元：标题、段落、列表项、表格单元格、图注、图表标题/图例、公式旁注、CAD 文字和脚注。禁止简单按固定字符长度切割整篇文本而破坏段落、表格和跨页上下文。

## 12.3 文档级上下文

* 提取文档标题、主题、行业、设备/工艺名称、章节层级、缩略语和术语表，形成文档上下文包。
* 翻译分块应带有必要的前后文、章节标题、源语言/目标语言和文体要求。
* 上下文包设置长度预算，按优先级保留全局术语、当前章节、邻近段落和必要引用，避免无界增长。
* 同一文档内同一术语应保持一致；若因语境必须变化，应记录术语例外及理由。

## 12.4 数值、单位和保护片段

翻译前识别并保护：数字、日期、编号、标准号、型号、序列号、尺寸、公差、单位、化学式、公式、URL、代码片段和专有名词。保护机制应采用占位符或结构化片段，翻译后逐项校验恢复。不得因语言习惯自动换算单位或改变小数精度。

## 12.5 术语管理

术语记录至少包括 sourceTerm、targetTerm、sourceLanguage、targetLanguage、domain、definition、partOfSpeech（可选）、preferred/forbidden、source、approvalStatus、version。支持文档级术语、项目级术语和全局术语；优先级需明确，冲突时提示用户或采用经确认的高优先级术语。

## 12.6 翻译质量检查

* 术语一致性：术语命中、漏用、错误替换和同词异译。
* 数字一致性：数字、单位、编号、标准号、日期和尺寸前后完全对应。
* 完整性：源文翻译单元与译文单元一一对应，不漏段、不重复。
* 结构一致性：标题层级、列表、表格行列、脚注引用和图注关系保持。
* 语义质量：否定、条件、义务、禁止、警告、因果、比较级、范围和限定语重点复核。
* 专业风险：法律责任、工程参数、安全警示、化学品名称和设备操作步骤列为高风险复核对象。

## 12.7 翻译记录

每个翻译单元保存 sourceText、targetText、sourceLanguage、targetLanguage、contextRef、terminologyRefs、provider、model、promptVersion、requestId、timestamp、qualityChecks、reviewStatus。不得只保留最终译文。

# 13\. 表格、图文关系与跨页结构

## 13.1 表格

表格识别应恢复行列结构、合并单元格、表头层级、单位、脚注、边框/无边框关系和跨页续表。原生 PDF 表格可结合文本坐标、矢量线条和区域结构恢复；扫描表格使用版面分析与 OCR。

## 13.2 图文关系

图表、公式、图片和工程图应与其标题、编号、正文引用、图例、注释建立关系。关系类型至少包括 CAPTION\_OF、REFERENCED\_BY、ANNOTATES、CONTINUES\_ON\_PAGE、CONTAINS、ADJACENT\_TO。

## 13.3 跨页对象

跨页表格、续页段落、跨页图注和章节延续应建立显式关系。不得把每页片段分别翻译后造成术语、句义或表格列语义断裂。

# 14\. Word 输出与文档重建

## 14.1 输出模式

| 模式 | 说明 | 适用场景 |
| :--- | :--- | :--- |
| 双语段落对照 | 原文段落后紧跟译文段落，保持标题/列表层级 | 审阅、合同、规范、技术说明 |
| 双栏对照 | 原文与译文左右分栏或表格并列 | 便于逐段比较；需注意长段落分页 |
| 译文版 | 仅输出目标语言，尽量重建原始版式 | 正式阅读和流转 |
| 原文+译文+审校信息 | 保留原文、译文及必要的审核标记/备注 | 高风险技术、法律和尽调文件 |

## 14.2 重建策略 A/B/C

| 策略 | 含义 | 适用条件 |
| :--- | :--- | :--- |
| A 原生结构重建 | 恢复为可编辑文本、表格、公式、矢量图表等 | 原始结构证据充分、识别质量达到阈值 |
| B 矢量/结构化重建 | 通过几何与数据算法重建曲线、统计图、流程图或部分工程图 | 几何/数据可可靠恢复，但原始对象结构不完整 |
| C 原始对象保留 | 保留高分辨率原图/原始嵌入对象，必要时叠加译文标注或附译文 | 复杂、低清、歧义或重建风险较高 |

A/B/C 是按对象可信度选择的处理策略，不是质量等级。一个文档内可以混合使用。禁止为了追求可编辑率，将低可信对象强制重建。

## 14.3 DOCX 技术实现

DOCX 生成应使用成熟、可维护的文档生成方案。候选可评估 docx 库或运行环境可用的等价方案；AI Studio 必须核验分页、表格、图片锚定、页眉页脚、字体、公式表达和复杂版式能力。不能只凭成功导出一个 DOCX 就判定版式重建完成。

## 14.4 输出检查

* 翻译单元完整率、段落顺序、标题层级、表格行列和图注引用完整。
* 数字、单位、公式、编号和尺寸与源文件逐项对照。
* 图片/图表清晰度、长宽比、位置、分页和裁剪正确。
* 页眉页脚、页码、目录、脚注和交叉引用按支持范围处理。
* 输出 DOCX 可正常打开、编辑和再次保存；必要时提供 PDF 预览。
* 版式无法完全复现时，明确标注差异，不得声称与原件完全一致。

# 15\. 引擎注册、调度与结果融合

## 15.1 引擎注册状态

| 状态 | 含义 | 允许对外表述 |
| :--- | :--- | :--- |
| DECLARED | 配置/代码中声明存在 | 已声明，未证明安装 |
| INSTALLED | 依赖已安装或服务可访问 | 已安装/可访问，未证明已加载 |
| LOADED | 引擎已成功初始化 | 已加载，未证明处理成功 |
| CALLED | 实际发起调用 | 已调用，未证明执行完成 |
| EXECUTED | 调用已完成 | 已执行，未证明输出有效 |
| OUTPUT_VALID | 输出通过结构/基本质量校验 | 输出有效，未证明真实样本达标 |
| SAMPLE_VERIFIED | 通过指定真实样本及指标验证 | 在明确样本和指标范围内已验证 |

状态必须由运行时事件和可检查证据驱动。禁止在模块注册表中预设 installed=true、loaded=true 或 verified=true。不得把 DECLARED、INSTALLED 或 LOADED 对外报告为“功能已实现”。

## 15.2 引擎路由

路由输入至少包括 objectType、sourceType、pageQuality、nativeEvidenceAvailability、language、requiredOutput、confidence、engineAvailability 和用户设置。路由策略可采用规则优先、能力评分和失败回退；复杂模型可辅助选择，但必须可解释、可追踪。

## 15.3 初步路由规则

| 对象/场景 | 优先路线 | 回退路线 |
| :--- | :--- | :--- |
| 原生 PDF 文本 | PDF.js 原生提取 | OCR 仅补缺失区域 |
| 扫描文字 | OCR + 版面区域 | 人工审核/原图保留 |
| 原生表格 | 文本坐标+矢量线条/结构恢复 | 版面模型/表格识别 |
| 扫描表格 | 版面分析+OCR+表格结构模型 | 原图保留并附译文 |
| 原生公式 | PDF 原生对象与排版结构 | 公式识别模型辅助 |
| 图片公式 | MFD/MFR 模型 | 原图保留+待审核 |
| 原生矢量图表 | 矢量路径+文字+几何算法 | 图像分析辅助 |
| 栅格曲线/统计图 | OCR+OpenCV+数字化算法 | 原图保留+待审核 |
| CAD 工程图 | 已验证 CAD 插件 | 原始图形保留 |
| 专业翻译 | Gemini Translation Provider | 经用户批准的替代 Provider |

## 15.4 结果融合

建议可信优先级：可信原生提取 > 专业确定性算法 > 专业识别模型 > 通用 LLM 推断。人工修订为当前审核版本，但必须保留修改前结果和理由。不同来源冲突时不得简单覆盖，应记录冲突对象、来源、差异、选择规则和审核状态。

## 15.5 去重与冲突

对象去重需综合页面、空间位置、内容相似度、对象类型、来源引用和父子关系。重叠对象不能一律删除：例如文本框与图表标题可能存在合理包含关系。合并/去重操作应保留被合并对象 ID 与来源证据。

# 16\. 任务管理、状态、日志与异常处理

## 16.1 任务模型

任务至少包括 taskId、documentId、createdAt、updatedAt、taskType、sourceLanguage、targetLanguage、settings、currentStage、progress、status、warnings、errors、outputRefs 和 version。任务与文档对象分离，允许同一源文件创建不同目标语种或输出模式任务。

## 16.2 进度

进度应由真实工作项完成情况计算，例如页面解析、对象识别、翻译单元、对象重建和导出。若无法精确计算，应显示阶段状态或 indeterminate，不得用固定时间增长、随机数或模拟百分比制造进度。

## 16.3 日志

日志至少包含 timestamp、level、taskId、stage、module、action、engineId、inputRef、outputRef、duration、status、errorCode、message 和 correlationId。日志不得只写“成功”，应能定位到实际调用、输入和输出。

## 16.4 异常处理

* 区分文件损坏、格式不支持、引擎不可用、API 限流、超时、模型输出无效、解析异常和用户取消。
* 支持可重试错误的指数退避或合理重试策略；不可重试错误应给出明确原因。
* 单页或单对象失败不应无条件导致整份文档丢失；允许局部失败并标注。
* 任务恢复时不得重复扣费或重复写入已完成结果；必要时使用幂等键。
* 异常信息面向普通办公用户表达，同时保留技术日志供诊断。

# 17\. GUI 与交互要求

## 17.1 界面保护

在现有程序基础上升级时，必须保留完整 GUI 布局、颜色体系、主要按钮、菜单层级、已有交互流程和用户已验证功能。除用户明确授权的界面修改外，不得因底层技术升级而重新设计界面。若实现确需调整，应先说明具体位置、原因和影响，并取得用户确认。

## 17.2 用户操作流程

1. 选择/指定文件或文件夹（按现有产品已支持的入口），查看文件清单和导入状态。
2. 选择源语言、目标语言、翻译模式和必要的专业领域/术语库。
3. 查看文档预检结果、页面缩略图和识别对象概况。
4. 启动处理并查看真实进度、阶段状态、警告和失败对象。
5. 查看译文、对象识别结果和待审核项；支持必要的人工修订。
6. 选择 Word 输出模式并导出，查看质量检查结果。

## 17.3 交互原则

优先采用普通办公用户能理解的术语。技术参数默认收敛到高级设置，不把复杂算法参数暴露为必填项。每个警告需说明影响和可采取的操作。用户可选择跳过某类对象，但系统必须记录跳过原因。

建议依赖方向：UI → Application → Domain；Application 调用 Engines contracts；Engine adapters 实现 contracts；Infrastructure 提供存储、API、日志和配置。Domain 不应直接导入 UI、Gemini SDK、PDF.js 或具体外部引擎。

## 18.2 文件职责审查

不得出现一个超大组件同时承担 PDF 解析、翻译、坐标换算和 DOCX 输出；也不得为了形式上的模块化制造大量无实际调用的空文件。模块必须有真实调用链、输入输出和测试证据。

# 19\. 核心数据结构与接口契约

## 19.1 通用引擎接口

每个引擎适配器至少实现：getCapabilities()、getStatus()、initialize()（若需要）、process(input, options, context)、validateOutput(output)、dispose()（若需要）。具体语言和签名可按框架调整，但语义必须一致。

## 19.2 处理输入

统一 EngineInput 应包含 taskId、documentId、pageId、objectId（对象级处理时）、sourceRef、sourceType、objectType、bbox、coordinateSpace、languageHints、contextRef、options 和 correlationId。原始二进制或大对象通过引用传递，避免在 JSON 中重复复制大型文件。

## 19.3 处理输出

统一 EngineOutput 应包含 engineId、engineVersion、executionId、status、outputType、payloadRef/payload、confidence（可空）、evidence\[\]、warnings\[\]、errors\[\]、metrics、durationMs 和 coordinateSpace。输出先经 schema 校验，再进入 Document IR。

## 19.4 版本兼容

Document IR、引擎接口和任务数据必须带 schemaVersion。升级字段时定义兼容策略；旧任务记录不得因程序升级而无法读取。

# 20\. 技术候选与替代评估机制

下表为推荐候选，不代表已集成或已验证。AI Studio 必须基于其当前运行环境、依赖安装权限、服务调用能力、文件大小/时长限制、成本和实际输出质量进行评估。

| 能力 | 首选候选 | 备选/替代方向 | 必须评估的重点 |
| :--- | :--- | :--- | :--- |
| PDF 原生解析 | PDF.js | 可补充其他 PDF 解析库 | 文本/矢量/图像对象提取、坐标、旋转、版本兼容 |
| 综合版面解析 | MinerU | Docling；或轻量版面模型 | 部署形态、API 可调用性、表格/公式/阅读顺序质量、成本 |
| OCR | 环境可调用的成熟 OCR 引擎 | 云端 OCR/模型视觉能力 | 中英老挝语覆盖、数字单位准确率、区域坐标、费用 |
| 公式识别 | Pix2Text（MFD/MFR）候选 | 同类公式检测/识别模型 | 模型可用性、语言/公式类型、LaTeX 结构准确率 |
| 曲线/统计图 | OpenCV + 图表数字化算法 | WebPlotDigitizer 类能力或自研轻量算法 | 坐标标定、系列分离、数据误差、浏览器/服务端兼容 |
| CAD | 用户已验证 CAD 插件 | 保持插件接口不变，按需要适配 | 真实调用接口、实体类型、坐标和文字回写 |
| 专业翻译 | Gemini | 经用户确认的其他 Provider | 语种质量、上下文长度、配额、成本、结构化输出 |
| DOCX | 成熟 DOCX 生成库 | 运行环境兼容的等价方案 | 分页、表格、图片锚定、公式、字体和可编辑性 |

## 20.1 替代方案评估表

| 评估维度 | 必须回答的问题 |
| :--- | :--- |
| 功能等价性 | 替代方案覆盖哪些原功能？缺失哪些能力？是否改变产品目标？ |
| 准确率/质量 | 有哪些公开基准或真实样本结果？关键指标和适用范围是什么？ |
| 部署与依赖 | 是否可在 AI Studio 实际环境调用？需要独立服务器、容器、系统软件或额外账户吗？ |
| 性能 | 单页/百页/大型文件的耗时、内存、并发和超时限制如何？ |
| 成本 | API 费用、计算资源、存储、调用次数和长期维护成本如何？ |
| 接口影响 | 是否改变 Document IR、Engine contract、UI、任务流程或输出格式？ |
| 失败回退 | 服务不可用、限流、低质量输出时如何降级？ |
| 维护风险 | 版本活跃度、许可证、社区、升级兼容和供应商锁定情况如何？ |

替代方案不得只写“更适合/更先进”。必须提供对比依据、缺失能力、用户可感知影响和建议。未经用户确认，不得擅自改变本规范的产品目标、核心数据契约、界面基线或输出要求。

# 21\. 质量评价与端到端验收

## 21.1 验收总原则

验收以真实业务文件和可复现测试样本为依据。必须区分单元测试、集成测试、真实样本验收和人工专业审校。测试报告需列出样本、版本、配置、运行时间、实际输出、指标和失败项。不得硬编码 PASS、伪造监控数据、使用固定置信度或以模拟样本冒充真实文件。

## 21.2 验收指标

| 能力 | 建议指标 | 验收要求 |
| :--- | :--- | :--- |
| 文件导入 | 文件读取成功率、页数/页尺寸一致性 | 与真实源文件元数据核对 |
| PDF 原生提取 | 文本覆盖率、对象定位偏差、矢量/图像提取完整性 | 抽样人工标注对照；原生对象坐标目标≤1 pt（适用范围内） |
| 版面/OCR | 区域 Precision/Recall/F1、CER/WER、阅读顺序准确率 | 按语言、扫描质量和页面类型分组报告 |
| 公式 | 区域检测 Precision/Recall/F1、结构准确率、误检/漏检率 | 包括目录、编号、表格标题等易误检负样本 |
| 图表 | 轴/刻度/图例识别率、数据点误差、系列识别率 | 有已知数据的样本对照，不接受只看视觉效果 |
| CAD | 实体/坐标/尺寸/图层一致性 | 使用插件真实输入输出及几何校验 |
| 翻译 | 术语一致性、数字一致性、完整率、专业审校结果 | 按文档/段落/高风险术语分别统计 |
| Word | 结构完整率、对象保留率、可编辑性、分页/版式缺陷 | 使用 Office/WPS 实际打开检查 |
| 工作流 | 任务完成率、失败可恢复率、重复执行一致性 | 真实任务日志与状态机验证 |
| 引擎调度 | 状态准确率、调用链完整率、失败回退正确率 | 逐项提供调用和输出证据 |

## 21.3 测试样本分层

* 基准样本：结构清晰、质量较高，用于验证基本能力。
* 复杂样本：多栏、混合对象、低清扫描、跨页表格、复杂公式、多系列图表。
* 负样本：目录、页码、普通编号、表格标题、非公式数学符号、图表背景线等，重点检验误检。
* 真实业务样本：来自设备、工程、法律、科研等实际资料；敏感内容由用户自行决定是否用于测试。
* 回归样本：每次修改后重跑，确保已通过能力不退化。

## 21.4 验收报告必须包含

* 软件版本、代码提交号、运行环境、依赖版本、模型版本和配置。
* 测试文件清单、文件哈希、页数、对象类型和样本标注来源。
* 每项指标的分母、分子、计算方式、结果和适用范围。
* 原始输出、可视化叠加图、错误样例和失败日志。
* 通过项、部分通过项、未通过项、未测试项分别列示。
* 禁止把“未测试”“未接入”“接口占位”写成 PASS 或已完成。

# 22\. AI Studio 整体评估报告要求

AI Studio 在编写或大规模修改代码前，必须先阅读本规范及当前仓库完整代码，提交一次覆盖全系统的可行性评估。此评估不是让 AI Studio 重新定义产品，而是核实实现路径、环境限制和技术候选，识别不适配项并提出平替。

## 22.1 必须评估的内容

* 当前项目代码、目录、依赖、界面、已有功能和调用链的完整盘点；区分可保留、需修复、需替换、无效/占位。
* 当前 AI Studio Build 运行环境可执行的前端、后端、外部 API、文件处理和长任务能力边界。
* 本规范各模块的可实现性、候选库/模型的实际可调用性、部署依赖、配额、成本和性能风险。
* Document IR、坐标体系、引擎接口、翻译上下文和 DOCX 输出之间的数据契约是否闭合。
* 全量逻辑代码树与当前仓库结构的映射，说明需要新增、修改、保留和删除的文件。
* 每项替代技术的功能损失、精度影响、成本影响、性能影响、用户操作影响和迁移影响。
* 当前 GUI 基线保护方案，明确不修改哪些组件、样式、按钮和操作流程。
* 端到端真实样本测试计划，以及当前无法验证的项目和原因。

## 22.2 报告结论分类

| 结论 | 定义 |
| :--- | :--- |
| 可直接实现 | 现有环境和依赖可支持，接口和验证路径明确 |
| 需增加依赖/服务 | 可实现，但需安装依赖、启用 API 或提供额外运行服务 |
| 需替代实现 | 原候选不适用，已提出功能等价或可接受的替代路线 |

| 当前不可实现 | 在当前环境存在明确技术限制，需用户决策是否调整范围 |
| 待验证 | 缺乏足够证据，必须设计最小真实验证，不得先宣称可用 |

## 22.3 用户决策门槛

AI Studio 评估报告提交后，由用户与技术顾问共同审查。凡涉及产品目标、用户操作、GUI、Document IR 核心字段、输出模式、专业质量标准、外部服务费用或数据流变化的事项，必须经用户确认后才能纳入最终实施基线。

# 23\. 整体建设要求与变更控制

## 23.4 完成定义

只有在完整工作流可运行、关键模块真实调用、输出有效、真实样本验收有数据、未通过项如实披露、GUI 未发生未经授权的漂移、部署和使用说明完整的前提下，才能称为某一范围内的可交付版本。任何未测试能力必须标记为未验证。
